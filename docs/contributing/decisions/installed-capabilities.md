# Installed capabilities

This contract is for contributors extending environment execution or generated surfaces: who
observes, decides and executes, who owns each generated file, and where the framework ends.

## Observation and execution

Application code runs the steps in order: observe, decide, execute, then check the result. The
CLI connects the pieces and prints outcomes; it is not the only place that may start execution.
Decision functions take typed observations and return the actions to take. One executor handles
process spawning, timeouts, output size limits, signals and undoing a partial run; it never picks a
stack, works out who owns a file, or decides what to delete.

Observe with the real Git and runtime commands instead of re-implementing their metadata
formats. Do not add a generic workflow language or a universal state-machine engine. A service
health result needs the start, status and identity stages, in that order, and test fixtures that
build one follow the same order.

An interrupted destructive operation retries against the request saved for it, including its
generation and the time window in which its actions are valid. A fresh plan may advance the
coordination revision but may not silently change the work. Even a reset that changed nothing
must finish by reading current coordination and finding the expected sole holder and an
unreleased lease.

Git comparison checks the remote selected by the current upstream, then rechecks the exact
ref and upstream after reading that remote's URL before returning a verdict.

## Generated ownership

Each generated file has one writer and is compared byte for byte by default. A harness that
needs a shared file gets a marked section cockpit owns; bytes outside it are kept and excluded
from drift checks. Overlay templates written by the consumer are generation inputs, so the files
they produce are checked too. The consumer's files outside the declared generated paths are not
the generator's to touch. The consumer owns the generated files in that they are committed and
reviewable; tailoring happens in overlay inputs, not in the generated bytes.

Each schema default is defined once. Its documented value and provenance derive from that
definition, so the generated editor schema and runtime validation agree.

## Framework and overlays

The framework and an overlay together provide the full capability. Mechanisms that repeat belong
in the framework; product-specific operations and values stay in the overlay. Data and vendor
operations declare their inputs, results and probes, and cockpit schedules and reports them.
Product models, fixture identities, environment loaders, vendor protocols and stub fidelity stay
out of framework policy. Integration tests show that the overlay behaves as intended.
