# Installed capabilities

<!-- cockpit:verified version=0.0.0 -->

This contract defines how contributors extend environment execution and generated surfaces.

## Observation and execution

Application code sequences bounded observations, domain decisions, execution, and
post-checks. The CLI binds adapters and renders outcomes; it is not the only place that may
invoke execution. One mechanical executor owns process spawning, timeouts, output bounds,
signals, and compensation. Pure decision functions receive typed observations and return
resolved actions. The executor never selects a stack, infers ownership, or decides what to
delete.

Use native Git and runtime commands for observations instead of reconstructing their metadata
formats. Introduce no generic workflow language or universal state-machine engine. Runtime
service health evidence requires admitted start, status, and identity stages in order;
fixtures that construct it follow the same sequence.

An interrupted destructive operation retries against its authenticated persisted request,
including its generation and action-validity windows. A fresh plan may advance the
coordination revision but may not silently change the work. Even an unchanged reset result
requires a final read of current coordination with the exact sole holder and an unreleased
lease.

Git comparison checks the remote selected by the current upstream, then rechecks the exact
ref and upstream after reading that remote's URL before returning a verdict.

## Generated ownership

Generated files have one writer and whole-file byte comparison by default. A harness that
requires a shared file gets an explicitly delimited owned section; bytes outside that section
are preserved and excluded from drift checks. Consumer-authored overlay templates are inputs
to generation, so their emitted files are checked too. Native consumer files outside declared
generated paths remain outside the generator's ownership. Consumer ownership means committed
and reviewable; tailoring happens in overlay inputs, not in generated bytes.

Schema defaults have one definition. Documented values and their provenance derive from that
definition, and generated editor schema and runtime validation remain aligned.

## Framework and overlays

The framework and overlay together provide the complete capability. Repeated mechanisms
belong in the framework; product-specific operations and values remain in the overlay. Data
and vendor operations declare inputs, results, and probes that cockpit schedules and reports.
Product models, fixture identities, environment loaders, vendor protocols, and stub fidelity
do not become framework policy. Integration proves the applicable overlay behavior.
